1. Executive Summary

Genio360 backend will be implemented as a dual-monolith architecture: a Core Platform Monolith handling business/identity/hierarchy/community modules, and a separate Hardware & Access Control Monolith handling device integration, MQTT, ANPR/vehicle access, and vendor SDK bridging. Both monoliths run inside the same AKS cluster, per region, and share the same MySQL, Cosmos DB, Redis, Service Bus, and Blob Storage instances. This is a deployment-level separation, not an infrastructure-level one — the cost increase is minimal (~8–10%) while unlocking independent release cadence and blast-radius isolation for hardware-related changes.

Why dual monolith: Hardware/vendor SDK integrations (Hikvision, MQTT bridge, ANPR, BLE) have a different release cadence, risk profile, and scaling pattern (spiky, event-driven) than core business modules (steady, HTTP-driven). Splitting them prevents a hardware vendor SDK bug from taking down resident-facing APIs, and allows the hardware monolith to scale-to-zero off-peak via KEDA — a saving not possible in a single monolith.
Timeline: Covering every module across the BRD set — the 19+ numbered business modules, the full Genio360 Priority list (Data Setup, My Profile, the ME Access Control cluster, Facial Recognition, Security Guard, Doorbell/IP Camera/VIDA Quantum, Directory, Dashboard, Switch Condo), the 24+ backend NestJS modules, both web apps, and continued mobile build-out — does not fit inside a 3-month window. Aligning the plan to the client's stated Genio360 Priority (Section 9) added roughly 15 modules that were not in the original module list, most of them concentrated in the Hardware/Access Control monolith. We are planning for 12 development sprints (Aug 2026 – 19 Jan 2027), per a client-mandated hard deadline to complete all development by 19 Jan 2027, followed by three post-development phases — UAT & Acceptance (Lite), QA & Stabilisation (Lite), and Pre-Prod Deployment (Lite) — running through 21 May 2027 go-live. Effort is estimated from the deep-dive BRDs we've already completed (Modules 12–18, ~25 user stories each on average) and scaled to the remaining modules by relative complexity.

Estimation Methodology

Effort per business module is derived from the already-audited BRDs (Modules 12–18), which average ~25 user stories each across 7 categories (Happy Path, Alternate, Exception, Validation, Permission, Notification, plus Business Scenarios). Modules are bucketed into three complexity tiers, calibrated against these audits:

TierStory Count / SignalEffortExample Modules
Simple<15 user stories, single controller, no hardware/payment dependency1 sprint (2 weeks), 1 engineerNotice/Wall, Feedback, Help & Support
Medium15–25 stories, 1–2 external integrations1.5–2 sprints, 1–2 engineersUnits, Documents, Service Request, Survey/eAGM, Home Services
Complex25+ stories, payment/hardware/concurrency logic (per Code Analysis findings in audited BRDs)2–3 sprints, 2 engineersFacility (slot locking), Wallet (concurrency), Vehicle (ANPR), Visitor, Intercom (relay/hardware logic)
Caveat: Modules without a completed Deep Dive BRD (Home Services, Survey/eAGM, Help & Support already reviewed; several others still at v1.0) carry higher estimation uncertainty. Sprint allocations below should be treated as ±1 sprint per module until each module's BRD reaches the same "Development Ready" depth as Modules 12–18.

Velocity & Capacity Model

Story points use the standard Fibonacci scale (1, 2, 3, 5, 8, 13). Average is ~3 points per user story once a story is broken down to controller/service/DTO/test granularity — a Simple module's ~15 stories work out to roughly 35–45 points, Medium to 55–70, Complex to 80–100+ once payment/hardware edge cases are factored in.

Worked example: IdentityModule + RbacModule (S2) is a Complex pairing, roughly 90 SP combined. At 24 SP/sprint Core capacity, that's ~3.75 sprints of raw effort — the plan compresses it into 1 sprint by having all 3 Core devs on it exclusively (no parallel module) and carrying JWT/MFA edge-case hardening into S3 as technical debt cleanup rather than blocking S2's "done" declaration. This pattern repeats for every Complex module in Section 7 — the listed sprint is when the module starts and gets a usable version, with the last ~15–20% of edge cases absorbed into the following sprint's regression pass.

Re-plan after S2: these velocity numbers are assumptions, not measured data. Run planning poker at the end of S1 to size the S2 backlog, then use actual S1–S2 throughput to re-forecast S3 onward. If real velocity comes in below ~20 SP/sprint for Core, scope — not the 19 Jan 2027 code-complete deadline (Section 9) — must be re-baselined immediately; the deadline is fixed and there is no sprint buffer to absorb slippage into.
